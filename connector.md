# HotelRADAR Direct Connector

## Purpose

The connector is a separate backend service owned by HotelRADAR Direct. It connects the Direct application with the existing Revenue Intelligence and Salesman systems through their approved normal-user/API/export capabilities.

It is an orchestration and audit layer. It does not replace either system and must never modify their code, databases, schemas, deployments, settings, users, or internal workflows.

## Responsibility boundary

| System | Connector responsibility |
|---|---|
| HotelRADAR Direct | Create the shared Opportunity ID; store traveller consent, verified request, support history, connector history and canonical cross-system timeline. |
| Revenue Intelligence | Receive a qualified request; provide hotel routing, hotel offers, booking confirmation, stay outcome and HotelRADAR commission result. |
| Salesman | Validate acquisition attribution; retain partner/campaign outcome and provide partner payout eligibility/settlement result. |

## Core rule: one opportunity

Every traveller request uses one immutable `external_opportunity_id`, generated by Direct.

```text
Example: OPP-20260804-0001
```

The same ID is included in every approved request, response, event, retry, Revenue record and Salesman record. The connector must never link records by traveller name alone.

## Connector flow

```text
1. Direct captures request and traveller consent
2. Direct verifies traveller contact
3. Connector validates referral/partner in Salesman (when present)
4. Connector creates or updates qualified opportunity in Revenue
5. Connector reads Revenue hotel route and offer events
6. Direct shows only approved/current offer to traveller
7. Connector reads Revenue booking and completed-stay result
8. Connector sends final funnel outcome to Salesman
9. Connector reads payout eligibility/settlement state
```

## Connector modules

### 1. Opportunity service

- Generates `external_opportunity_id` and opaque traveller `public_token`.
- Stores Direct-owned request, verification and consent data.
- Enforces canonical status transitions.
- Creates immutable timeline events.

### 2. Revenue adapter

Permitted capabilities:

- Create or update a qualified opportunity in Revenue.
- Read Revenue routing, offer, booking, stay and commission outcome.
- Invoke only explicitly approved normal-user/API actions.

The adapter must not infer a booking confirmation or completed stay. It displays only values returned by Revenue.

### 3. Salesman adapter

Permitted capabilities:

- Validate partner, campaign and referral code.
- Create/update approved attributed funnel record.
- Send qualified, booking-confirmed and completed-stay outcome.
- Read partner payout eligibility and settlement state.

The adapter must preserve original attribution and never create a duplicate payout opportunity.

### 4. Job queue and exception service

- Queues external work outside the traveller web request.
- Uses retry with exponential backoff for temporary errors.
- Sends exhausted failures to an operator-visible exception queue.
- Records safe failure details and last successful sync time.

## Canonical lifecycle

```text
draft → verification_pending → verified → qualified → routed
→ hotel_notified → offer_received → offer_sent → traveller_accepted
→ hotel_confirmed → stay_completed → commission_due → settled
```

Side states: `more_details_needed`, `hotel_declined`, `offer_expired`, `cancelled`, `issue_review`, `connector_failed`.

Only Revenue-originated approved outcomes can move an opportunity to `hotel_confirmed`, `stay_completed`, `commission_due`, or `settled`.

## Reliability and safety requirements

- Every external write has an idempotency key based on opportunity ID + action + version.
- Repeating an event must never create another opportunity, offer, booking, commission or payout.
- Connector uses dedicated least-privilege accounts, never administrator accounts.
- No direct database connection to Revenue or Salesman.
- Never log passwords, API keys, OTPs, payment data or unmasked traveller PII.
- All data transfer uses TLS; sensitive Direct data is encrypted at rest.
- If Revenue is unavailable, Direct retains the request as `qualified` and shows a truthful pending state.
- If Salesman is unavailable, attribution becomes `pending`; Direct does not promise a partner payout.
- If an offer cannot be verified from Revenue, it is not shown to the traveller.

## Required operator exceptions

| Exception | Owner action |
|---|---|
| Revenue sync failed | Retry or contact Revenue operations; do not manually claim hotel confirmation. |
| Salesman referral conflict | Hold attribution; request Salesman owner decision. |
| Hotel non-response | Follow hotel SLA/escalation process; update traveller honestly. |
| Price/offer change | Ask hotel for revised offer and require traveller re-acceptance if material. |
| Cancellation/no-show | Await Revenue outcome before any commission/payout action. |
| Duplicate opportunity | Link/close through auditable issue process; do not delete history. |

## Connector release criteria

- [ ] Dedicated integration access works for both systems.
- [ ] An opportunity is created and located by `external_opportunity_id` in both systems.
- [ ] Duplicate/retry tests are safe.
- [ ] Revenue offer, booking, stay and commission results sync correctly.
- [ ] Salesman attribution and payout results sync correctly.
- [ ] Connector failures appear in Direct with a named next action.
- [ ] No connector capability changes either external system outside the approved interface.
